# NSV 舰队序列化与物化设计

版本：v2 · 2026-09-21

## 1. 范围与定位

本文定义 AI 舰队在星区休眠/离场时如何从实时 grid 转为战略数据、以及唤醒/抵达时如何还原的具体机制。它是 `feature_nsvstrategicoperations.md` 里"去物化/物化"抽象规则的**落地实现方案**，选择了更简单的一组具体决策：

- 用一个显式 marker component 声明"哪些 grid 可数据化"，而不是运行期到处推断；
- 用 **holding map（S2）** 保存离场 grid，不做 yaml 序列化、不删实体；
- 用**地板数**表达舰船完整度，损伤=删地板、修复=加地板。

本文不改变 `feature_persistentsectors.md` 的承诺：同一次服务器运行期内保留实体、UID、库存、损伤。跨服务器重启、磁盘存档不在范围内。

## 2. 两层划分

星区休眠时，节点上的对象按"睡着时需不需要数据模拟"分两层，规则完全不同：

| 层 | 例子 | 休眠行为 | 是否进 strategy |
| --- | --- | --- | --- |
| 纯布景 | 陨石、小行星、碎片 | 就地 pause，原样冻结（现有 sleep） | 否 |
| 需数据模拟 | AI 舰队、空间站 | 转为数据，grid 移入 holding map | 是 |

划分轴不是"AI 舰队 vs 空间站"，而是"睡着时是否需要继续演化/移动"。只演化位置、完整度、攻击力的对象才进第二层。玩家船不带 marker，永不进入本机制。

## 3. NsvSerializable component

```csharp
[RegisterComponent]
public sealed partial class NsvSerializableComponent : Component
{
    public string FleetId = string.Empty;
    public string ShipId = string.Empty;
    public ulong BindingGeneration;
    public int TargetFloorCount;      // 100% 完整度基准，spawn 时固定
    public string? RepresentationFailure;
}
```

**component 是"能序列化"的必要声明，不是"此刻就能"的充分条件。** 带 marker 只表示这个 grid 设计上可数据化；实际能否序列化由运行期闸门（见第 7 节）判定。

**它只管序列化 + 身份绑定，不管 AI 行为。** AI 行为由独立 component 承担，在实例化后单独挂上、自行重建运行态（当前目标、寻路等瞬态不进数据记录）。这样也允许序列化非 AI 的 grid（如无人空间站）。

## 4. Born-bound：身份即刻绑定

generator 从模板 spawn 出可序列化 grid 的那一刻，strategy 就分配数据记录并绑定身份。"必定绑定一个数据"绑的是**身份**（FleetId/ShipId），不是 blob。

**ID 分配权威**：FleetRegistry 是唯一分配者，别处禁止构造 ID。用每回合单调计数器加前缀（`fleet-N` / `fleet-N.ship-M`），可读、日志好认、永不复用；因不跨重启，无需持久化协调。

因此 `Live` 的语义是"grid 是数据记录 X 的当前活体"：数据记录存战略位置，grid 是该身份的活体形态，两者是同一实体的两个面，不是双权威。权威随状态单向切换（第 6 节）。

## 5. 三层数据

序列化一支 AI 舰队时，记录存三层，职责分开：

| 层 | 内容 | 谁用 | 何时写 |
| --- | --- | --- | --- |
| 重建来源 | grid 本身（S2：停在 holding map 上的活体） | AI 实例化时精确还原 | 序列化时 |
| 抽象数值 | 完整度（= 地板数比例，见第 8 节）；攻击力（派生） | strategy 抽象战斗 | 序列化时派生，睡眠期被改写 |
| 战略位置 | 节点 / Travel / Faction | strategy 跨区移动 | 移动时改写 |

攻击力**是派生量**，不单独存。提供一个"计算战斗力"接口：读取 grid 上带炮塔 component 的物体累加得出基础战力，再乘当前完整度。抽象战斗只损耗完整度一个变量，攻击力自动跟降。弹药本版一并派生（不单独追踪"弹药打光但船体完好"，以后需要再拆成独立变量）。

## 6. S2：holding map 存储

**离场 grid 不删除、不序列化成 blob，而是 reparent 到一张全局常驻暂停的 holding map。**

- holding map 全局唯一，服务器运行期创建一次，永远 paused。
- 上面的 grid 保活、UID 不变、状态原样保留，仅不模拟（等同现有 sleep 的暂停开销）。
- 上面的对象必须禁用 AI、不参与物理/网络交互、不触发 encounter（与 sleeping sector 内实体同等的隔离保证）。

**权威随位置单向切换：**

| 位置 | 权威 | 完整度含义 |
| --- | --- | --- |
| 目标 sector map（Live） | grid | 由实时战斗直接改 grid，数据里的完整度是旧的 |
| holding map（数据态） | 数据记录 | grid 冻结不动，抽象战斗只改记录里的完整度数字 |

- **序列化（grid→数据）**：reparent 到 holding map；`完整度 = f(grid 当前地板数)` 拍照进记录。
- **实例化（数据→grid）**：从 holding map reparent 回目标 sector map、解暂停；按记录完整度删地板到目标地板数（第 8 节）。

选 S2 而非真序列化（S1，grid→yaml blob→删实体）的理由：无 UID remap、绝对无损、实现简单，且绕过"RT 对活体 grid 能否无损 round-trip"这一未验证风险。代价是实体常驻内存（但暂停，模拟开销可忽略）。S1 留作以后内存吃紧时的优化。

**跨区移动天然支持**：舰队在战略图"移动"只改数据记录的节点，grid 一直停在同一张 holding map 上不用真搬。目的地 sector 醒来时，才把"数据节点 == 该 sector"的 grid 从 holding map 拉过去。

## 7. 序列化/实例化的触发与闸门

### 触发时机

**序列化 ⟺ 睡眠；实例化 ⟺ 唤醒。** 实例化是给实战用的——sector 不醒，没人做战术交互，就没理由造活体 grid。

| 事件 | 序列化 | 实例化 |
| --- | --- | --- |
| 整个 sector 睡 | 批量：所有第二层对象移入 holding map | — |
| 整个 sector 醒 | — | 批量：数据节点==本 sector 的对象移回 |
| 单支 Live 舰队从**醒着**的 sector 离场 | 单个：该 grid 移入 holding map | — |
| 单支数据舰队抵达**醒着**的 sector | — | 单个：该 grid 移回 |

**两个睡着的 sector 之间移动舰队：不唤醒任何一方、不实例化**，只在战略层改数据节点。抵达一个**睡着**的目的地也不实例化，以数据身份挂在该睡着节点上，等它将来醒了才实例化。

**战斗只在星区（节点）内发生，航行途中不战斗。** 舰队处于 Travel 状态时只推进位置，不参与任何抽象战斗；抵达节点后才可能与该节点的其他数据舰队结算。

### 唤醒时的重生成闸门

sector 唤醒**不能无脑重生成所有曾在此序列化的对象**——一艘船睡眠期间可能已在战略图开走。唤醒时必须问 strategy：**只实例化"数据记录当前节点 == 本 sector"的对象**，开走的不在这儿还原。这依赖节点驻留索引（见 strategic operations 文档）。

### 离场引用闸门

一支舰队只有对"自己舰队之外"没有活引用时才能序列化离场。序列化那一刻检查：

- 停靠在留在原地的空间站/其他 grid 上 → 先强制脱靠，否则挡下离场；
- 被某 encounter 的 objective 指着（它是任务目标）→ 不许走，或先把该 encounter 判完/判失败；
- 舰队内部多 grid 互相引用（编队几艘船）→ **一起序列化**，不算跨引用。

无法安全处理的引用记入 `RepresentationFailure`，返回失败，不删实体后等扫描修复。

## 8. 完整度 = 地板数模型

**完整度 = 当前地板数 / 满编地板数**（满编 = `TargetFloorCount`，spawn 时固定的 100% 基准）。当次实例化要还原到的地板数称**目标地板数** = round(完整度 × 满编)。损伤=删地板，修复=加地板。这样完整度是从 grid 直接数出来的派生量，无需单独存、不会 desync；未来做模拟损伤/修复也只是加减地板。

- **只存一份满编地板坐标集**（spawn 时拍照）当参照。删除/修复顺序用**可计算的比较器**（如按到质心距离、外圈优先、同距离坐标 tiebreak），不额外存"删了哪些"——给定坐标集 + 比较器，"剩 X% 时保留哪些"完全确定。
- **删地板顺序：外圈向内**。比较器先做好接口，具体规则和实现放到后面（首版可留占位实现）。
- **套伤害是目标式、幂等的**：规则是"删到地板数 == 目标地板数"，不是"扣掉 20%"。实例化重试/发布日志重放多次都收敛同一状态，不越恢复越残。
- **修复 = 加地板**：从满编参照集里把当前缺的、最靠内的补回。
- **删地板不删地板上的东西**（墙、机器）。可能出现"地板没了、墙飘着"，AI 船粗模拟可接受，需知晓。

### 伤害双向流

- **Live 态**：实战打 grid → 直接删地板/炸设备，是**任意**炸洞、不遵守比较器顺序。数据完整度此刻不管，下次序列化时按**地板数量**重新派生（真实战损被"拍照"进数据）。
- **数据态**：grid 冻在 holding map。抽象战斗只改记录里的完整度数字，实例化时按比较器顺序删地板还原。

**不对称**：比较器顺序只管数据态的抽象损伤/修复；Live 态战损是真实物理、形状任意，完整度只按地板数量算，不要求"干净的外圈缺失"。

举例：序列化拍照时 80%（此前实战在船中间炸了洞，无损保留那个形状）→ 数据态抽象战斗又打到 60% → 实例化时先移回（物理还是那个 80% 的形状），再按比较器删外圈到 60%。重试再跑仍收敛 60%，不叠加。

## 9. 与现有代码的衔接

- `MustRunTaskBlocker` 目前会触发 `RequestWake`（`NsvBluespaceSectorLifecycleSystem.cs:263`），属测试用途、正常不应出现。实现"从睡眠态直接序列化"时，不要引入新的会触发 `RequestWake` 的路径。
- 位置写入只经 FleetRegistry 发布 API，禁止分别写 grid 位置和数据节点。
- holding map 上的 grid 不得被 travel 系统的"缺 FTLComponent 即 stale"清理逻辑误删。
- 现有 `NsvFleetShip`（仅 Id/GridPath）需扩展为第 3/5 节的字段，或由 component + 记录承载。

相关文件：舰队数据 `Content.Server/_NSV/Bluespace/Strategy/`；生命周期 `Content.Server/_NSV/Bluespace/Sectors/`；encounter `Content.Server/_NSV/Bluespace/Encounters/`。

## 10. 非目标、未决与前置验证

### 非目标

- 跨服务器重启恢复、磁盘存档；
- 玩家船数据化（不带 marker）；
- 通过重载模板隐式修复战损（修复=显式加地板，不是模板重建）；
- 攻击力独立于完整度的建模（首版派生）。

### 已定的实现细节

- **不设 holding map 容量上限**（首版）。
- **删地板比较器先做接口、后做实现**：顺序为外圈向内，首版可留占位实现，具体规则和实现放到后面。
- **布局参照**：只存一份满编地板坐标集（spawn 时拍照）；删除/修复用可计算比较器，不额外存被删集合。
- **战斗力接口**：读取 grid 上炮塔 component 累加基础战力 × 完整度；弹药本版派生。

### 未决

- 比较器的确切规则（质心距离的 tiebreak 细节）在实现阶段定并测试。

### 前置验证

- **地板数与完整度的映射**在目标 AI 舰船原型上是否合理（船体形状差异大时，地板比例是否能代表战力）；
- holding map 上暂停 grid 的隔离是否彻底（AI/物理/网络/encounter 全部不触发）；
- reparent 到 holding map 及移回是否保持所有相关状态与引用。

## 11. 验收要点

1. 带 marker 的 grid 睡眠时移入 holding map、UID 不变；纯布景就地冻结。
2. 唤醒只实例化数据节点==本 sector 的对象；已开走的不在原节点重生。
3. 两个睡着 sector 间移动舰队不唤醒、不实例化，仅改数据节点。
4. 数据态抽象战斗改完整度；实例化按完整度删地板到目标值，重放收敛同一结果。
5. Live 态实战战损，下次序列化时完整度正确重新派生。
6. 停靠/被 objective 引用的舰队序列化前被挡或先解引用；编队多 grid 一起序列化。
7. holding map 上的 grid 不被 stale 清理误删，不参与模拟/交互。
8. 攻击力随完整度派生下降，无需单独存储。

## 12. 实施顺序

按依赖顺序切分，每个 P 阶段可独立验证。

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **P1 身份与记录** | `NsvSerializableComponent`；FleetRegistry 的 ID 分配（`fleet-N` / `fleet-N.ship-M` 单调计数器）；born-bound 绑定；三层数据结构。无 grid 移动，纯数据 + 单测。 | — |
| **P2 holding map + 单支往返** | 建全局暂停 holding map；grid ⇄ holding map 的 reparent（序列化/实例化）与隔离验证。只做"单支 Live 舰队离场/抵达**醒着** sector"这一条最简路径。 | P1 |
| **P3 完整度与战斗力** | 满编地板坐标集拍照；删地板比较器**接口**（占位实现，外圈向内）；目标式幂等删地板/加地板；战斗力接口（读炮塔 component × 完整度）。 | P2 |
| **P4 批量 + 睡眠/唤醒挂钩** | 整 sector 睡→批量序列化；醒→按节点驻留索引批量实例化（含唤醒重生成闸门）。 | P3；**strategic ops** |
| **P5 离场引用闸门** | 脱靠、encounter objective、编队多 grid 一起序列化；`RepresentationFailure` 失败路径。 | P2 |
| **P6 抽象战斗接入** | 数据态战斗改完整度；途中不战斗；实例化按比较器套伤害还原。比较器真实实现（替换 P3 占位）可放此。 | P3、P4 |

### 跨文档依赖

P4 的"睡眠时序列化、唤醒时实例化"依赖 `feature_nsvstrategicoperations.md` 尚未实现的能力，本文档不重复定义，仅引用：

- **RequestWake 改 handle**（§10.3、§12）：唤醒可异步跨帧，实例化在恢复发布阶段进行。
- **节点驻留索引**（§4）：唤醒重生成闸门靠它判断"数据节点 == 本 sector"。
- **Node 资源协调**（§6）：序列化/实例化的批量写入须在 Node owner 下串行，不绕过预约。

因此 P1–P3、P5 可先行（不碰生命周期）；P4、P6 卡在 strategic ops 对应阶段完成之后。
